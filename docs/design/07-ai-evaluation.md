# 07. AI評価システムの拡張性

対応事項: **8. AI評価システムの拡張性**

## 設計原則

1. **評価エンジンをアプリ本体から分離**し、独立してバージョンアップできるようにする。
2. **スコアは「入力データ + エンジンバージョン」から再計算可能**にする。
   基準改定時に過去物件を新基準で再評価でき、基準の一貫性を保証できる。
3. MVPは「ルールベース + AI補助」の単純な構成で始め、**インターフェースだけ将来形にしておく**。

## 評価パイプライン

```
[入力] 物件構造化データ + 写真 + 外部データ
   ↓
[Stage1] データ充足チェック（必須項目・写真枚数・信頼度）
   ↓
[Stage2] 定量評価（ルールベース）          ← MVP はここが主役
   ・立地: 駅距離 / 都市計画 / 学区 / ハザード
   ・資産性: 周辺成約価格との乖離（不動産情報ライブラリAPI）/ 築年 / 管理状態
   ・流動性: エリア人口動態 / 同種物件の流通量
   ↓
[Stage3] 定性評価（Claude API 補助）
   ・写真から: 室内状態・明るさ・リフォーム要否の所見
   ・概要書・備考から: 告知事項・懸念点の抽出
   ・「おすすめ理由 / 向いている人 / 注意点」の下書き生成（LLMOコンテンツ）
   ↓
[Stage4] 合成: 総合スコア（100点満点）+ ランク（S/A/B）+ 改善提案
   ↓
[出力] evaluations レコード（engine_version 付き）→ 社内審査へ
```

## エンジンのバージョン管理

```
evaluation_engine/
  config/
    v1.0.0.yaml     ← 評価軸・重み・閾値を宣言的に定義
    v1.1.0.yaml
  rules/            ← 定量ルールの実装
  prompts/          ← Stage3のプロンプト（バージョン管理対象）
```

```yaml
# v1.0.0.yaml（例。実際の重みは非公開資産として管理）
version: "1.0.0"
publish_threshold: 85
axes:
  location:   { weight: 0.30, rules: [station_distance, hazard, school_district] }
  asset_value:{ weight: 0.30, rules: [price_vs_market, built_year, management] }
  liquidity:  { weight: 0.20, rules: [area_demand, stock_volume] }
  condition:  { weight: 0.20, rules: [photo_assessment, disclosure_check] }
```

- **重み・閾値はコードでなく設定ファイル**に置く。基準改定=新バージョンのYAML追加。
- `evaluations.engine_version` により「この物件はどの基準で85点を超えたか」が常に追える。
- 設定ファイル・プロンプトは**プライベートリポジトリの秘匿領域**として扱う
  （ブラックボックス方針のコア資産。クライアントに一切送らない・APIレスポンスに含めない）。

## AI（Claude API）の使い方と精度担保

| 用途 | モデル | 出力 |
|------|-------|------|
| 概要書の構造化抽出 | claude-sonnet-5（vision） | JSONスキーマ強制 + 信頼度 |
| 写真の定性評価 | claude-sonnet-5（vision） | 所見 + 減点候補フラグ（点数は出させない） |
| コメント下書き生成 | claude-sonnet-5 | おすすめ理由/向いている人/注意点 |
| 大量バッチ再評価 | claude-haiku-4-5 | コスト最適化 |

- **LLMに最終スコアを直接出させない。** LLMの役割は「観察・抽出・文章化」に限定し、
  点数化は決定的なルール（Stage2/4）が行う。同じ物件は何度評価しても同じ点数になること
  （再現性）が、認定制度の公平性・監査可能性の土台。
- LLM出力には必ず人間確認ステップ（社内審査）が入る設計を維持する（企画書方針そのまま）。

## 拡張ロードマップ

| Phase | 拡張 | 準備しておくこと（MVP時点） |
|-------|------|--------------------------|
| 1 | ルールベース + AI所見 | 上記構成 |
| 2 | 成約データの蓄積 → 重みのデータドリブン調整 | 成約結果・商談結果をDBに記録しておく（listings.status遷移が学習データになる） |
| 2 | エリア拡大対応 | ルールの閾値をエリア別に持てるYAML構造（`overrides: {prefecture: …}`） |
| 3 | 将来価値予測（価格予測モデル） | 物件×時点の価格履歴を price_histories に貯める |
| 3 | 会員向け「AI分析レポート」商品化 | 評価出力に「社内向け/会員開示可」のフィールド区分を最初から持たせる |

## 外部データソース（合法・公式のみ）

- 不動産情報ライブラリAPI（国交省）: 成約価格・地価
- 国土数値情報: ハザード・都市計画・駅・学区
- e-Stat: 人口動態
- ※これらはMVP時点ではCSV手動取込でもよい。取込テーブル（`market_data`）だけ用意しておく。
